# Methodology

The task is retrieval of annotated evidence-bearing **documents** for scientific claims. No training, sentence selection, reranking or verification is performed. Every mode uses the same full corpus, dev claims, pinned MiniLM weights, original SentenceTransformer mean pooling, 384-dimensional float32 embeddings, 256-token truncation, and L2 normalization. Long abstracts can be truncated: this is an explicit model limitation shared across modes.

## Dataset and ground truth

The actual Hugging Face repository `allenai/scifact` contains a legacy Python loading script with `corpus` and `claims` configurations. Corpus has the `train` split; claims has train, validation (official dev) and test. Inspection is cached along with the upstream commit. The loader downloads exactly the official archive referenced by that script and by the original AllenAI repository, avoiding execution of remote dataset code. It preserves original JSONL nested evidence annotations. The HF expanded-row schema is also supported by grouping claim IDs and unioning evidence document IDs. Cited document IDs are **not** relevance labels.

The full corpus is a shared inference collection, not a training split. Original claim splits are preserved and ID-disjointness checked. Train claims are never used for embeddings evaluation, fine-tuning or tuning; test claims remain unlabeled and are never evaluated. Evidence documents can legitimately occur across claim splits because the corpus is shared. Titles and ordered abstract sentences form `title + newline + space-joined abstract`. Original sentence strings and ordering remain available independently. Structured abstracts in this release are also ordered sentence lists. Malformed/missing/empty fields, invalid evidence references, rationale indices and duplicate corpus IDs cause explicit validation failure rather than silent dropping.

Quality is macro document Recall@1/5/10: fraction of each claim's annotated relevant documents retrieved. This is not hit-rate when a claim has multiple relevant documents. Full-corpus MRR and MRR@10 are both reported; binary nDCG@10 uses the number of annotated relevant documents for ideal DCG. Claims without evidence are excluded from these averages and counted separately. Missing annotations do not prove irrelevance. These metrics describe agreement with incomplete annotations and do not measure factual verification accuracy.

## Execution modes

Serial CPU sets relevant OpenMP/BLAS environment variables before numeric-library imports, limits PyTorch intra-op/interop, FAISS, and loaded native thread pools to one, then verifies the limits. Batch size is one, DataLoader workers zero, preprocessing and online requests sequential. Model initialization can involve file I/O; the timed inference/search configuration is single-threaded.

The serial index searches one query per FAISS call (`chunk_size=1`), including the corpus evaluation pipeline. Parallel configurations use batched searches. The RAM sampling thread is an observer, not a parallel retrieval worker; its overhead is present across configurations.

Parallel CPU uses ordered `ThreadPoolExecutor` preprocessing and native PyTorch/FAISS compute threads with batched inference/search. Python string assembly is GIL-limited and may slow down with threads; the meaningful numerical parallelism is inside PyTorch and FAISS. DataLoader workers remain zero, avoiding nested process/thread oversubscription. Threads and preprocessing workers are independent controls.

CUDA inference uses inference mode, no gradients, pinned host tensors, nonblocking transfers and synchronized timers. Default batch size is 64 with four requested tokenization DataLoader processes. A RAM preflight caps worker processes using available memory minus a 1 GiB reserve and 768 MiB per spawned worker; requested/effective counts and the reason are recorded. This is a conservative resource safeguard, not a measured optimum. Windows spawn overhead is measured against zero workers. Each worker has one PyTorch thread and reproducible seeds. The same resident model is used across trials. An OOM halves the batch size and restarts that encode operation, preserving order; every reduction is recorded. A size-one OOM fails clearly. The measured duration includes recovery work.

Hybrid mode has CUDA embeddings and CPU FAISS `IndexFlatIP`. Optional `torch_cuda_exact` stores document vectors on CUDA and performs float32 inner products. Queries are chunked and chunks shrink on OOM. All search is exact. For a stable cutoff on ties, both backends rank by score descending then original corpus index ascending. This implementation obtains full scores/rankings before selecting k, imposing additional sorting cost; results must not be generalized to optimized FAISS top-k-only workloads. Numerically near-tied CPU/GPU scores may change order; validation allows score-equivalent replacements within the declared tolerance. CUDA results are checked against CPU exact search on identical vectors, and mode embeddings/rankings are checked against the saved serial baseline before warm timings.

Native Windows GPU FAISS is not assumed. The official distribution lists CPU packages for Windows, GPU packages for Linux: https://github.com/facebookresearch/faiss/blob/main/INSTALL.md . WSL2/Linux could support a separate GPU FAISS experiment but requires separate environment validation and explicit authorization before installation; none is installed here.

## Timing and statistics

Offline stages: data loading, preprocessing, document embedding, index construction. Online stages: claim embedding and search. `end_to_end_s` rebuilds the full pipeline with a resident model. `cold_total_s` additionally includes first model initialization. Cold means application first-use of model initialization and the pipeline in a fresh configuration process, not flushed filesystem caches. Core library imports occur before timing and are excluded; the first Sentence Transformers import happens inside model initialization and is included. Downloads are excluded. Serialization, evaluation and parity checks are excluded from timed stage totals. Claim loading and small orchestration overhead explain differences between summed named stages and end-to-end time.

Batched online throughput and amortized batch latency are distinct from actual one-request latency. Each warm trial additionally times up to 30 sequential dev requests with zero DataLoader workers to avoid spawning workers per request, using the same model/device/index. Mean, median, P95 and raw embedding/search samples are saved. These 30 claims form a fixed deterministic latency sample, not the full effectiveness set. Larger latency samples can be requested.

Each configuration has a first-use measurement, explicit warmup, and five warm repeats by default. Each repeat rebuilds embeddings and indexes fairly. `perf_counter` wall times include CUDA synchronization and CPU/GPU transfers. Raw trials are preserved. Summary mean, sample SD, median and Student-t 95% CI across trials are reported. These are descriptive CIs conditional on this laptop/workload; repeats on one machine do not establish population generalization. Speedups are ratios of mean times, without an inferential confidence interval for the ratio.

CPU embedding efficiency = embedding speedup / native compute threads. Here one compute thread is the numerical worker; Python preprocessing worker count is logged independently and is not the denominator for transformer inference. GPU speedups are heterogeneous comparisons and have no CPU efficiency. Speedups are only generated for equal document/query counts and workload kinds. Preprocessing overhead and batch gains mean CPU comparisons are controlled configurations, not a pure thread-only scaling law.

Peak RAM is sampled process-tree RSS every 20ms (includes DataLoader children; can double-count shared pages and miss brief peaks). CUDA peak allocated/reserved bytes use PyTorch counters and exclude allocations by other programs/driver. FAISS serialized index size is 45-byte header plus float32 vector storage for this flat index. CPU/GPU telemetry and AC power are recorded before/after each configuration. No system settings, power policy or external workloads are changed automatically.

## Reproducibility and limits

Python, NumPy, PyTorch CPU/CUDA and DataLoader seeds are 42. TF32 and cuDNN benchmarking are disabled; deterministic PyTorch algorithms and CUBLAS workspace configuration are enabled. Different GPU/library versions may still produce small numerical differences, so parity uses tolerances rather than bitwise identity. Dataset archive, individual files and model contents have SHA-256 checksums. Revisions, package versions, hardware, Git commit (if available), configurations and raw samples accompany runs.

SciFact is small: tokenization, Windows worker startup, transfers, sorting, and launch overhead can dominate. A slower parallel run is a valid result. Repeated-document scaling is explicitly a compute-only experiment with no evidence-quality claims. SciFact-Open has not been downloaded: its corpus size and protocol need a separate audit and approval before any multi-gigabyte transfer. The fixed configuration order can introduce thermal/order effects; a publication should replicate randomized/interleaved configurations across sessions and report power/clock conditions.

The initial measurements delivered with this project were collected through Codex's workspace-write command sandbox on the detected Windows hardware. Process-launch, filesystem/security and runner effects were not independently isolated. Worker overhead conclusions therefore apply to this collection context; repeat the supplied commands in ordinary PowerShell before generalizing them to native-host Windows performance. Relative comparisons share the same runner, but that does not remove backend-specific process-startup effects.
